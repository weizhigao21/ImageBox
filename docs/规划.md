# ImageBox 未来规划（P1–P4）

> 制定日期 2026-11-13　|　基于 v0.3.1 现状
> 执行原则：优先做复用度高、能直接挂在现有「模块即插件」框架上的能力，识别类模型功能放后。

## 规划依据

项目最大的资产是「模块即插件」框架：新模块只需实现 `BaseModule` + `param_spec()`，
参数面板、批量、进度、取消、预设全部自动获得。排序原则：

1. 优先补齐已占位模块（框架已接好，只差实现）；
2. 其次做零模型依赖的通用能力（成本低、收益大）；
3. 识别类功能依赖权重管理扩展，放中期；
4. 框架级改动（Pipeline 串联）影响所有模块，放最后。

## P1 · v0.4 补齐占位模块（优先级：最高）

| 功能 | 与图片处理的关系 | 说明 |
|---|---|---|
| 超分 superres | 直接相关（优化） | Real-ESRGAN ONNX 版；参数：模型选择 / tile 分块 / tile 重叠；显存 11GB 需 tile 处理大图 |
| 裁剪 crop | 直接相关（编辑） | 批量按比例裁剪 / 智能主体裁剪（复用 matting 的 mask 输出）/ 去白边 |

- 依赖：ONNX 推理框架、`downloads.py` 权重下载、`device.py` 设备检测——全部已存在。
- 预期产出：2 个可用模块 + smoke 测试 + README 更新，`PlaceholderModule` 清零。

## P2 · v0.5 通用处理能力（优先级：高，成本低收益大）

| 功能 | 与图片处理的关系 | 说明 |
|---|---|---|
| 格式转换与压缩 | 直接相关（格式转换/优化） | PNG/JPG/WebP/AVIF 互转，质量参数、目标体积、EXIF 元数据清理；纯 cv2/Pillow 实现 |
| 基础编辑 adjust | 直接相关（编辑） | 缩放/旋转/翻转、批量加文字或图片水印、亮度对比度锐化 |
| 批量重命名/尺寸规整 | 直接相关（优化） | 文件名模板（复用 `io_utils` 命名模板）、统一最长边 |

- 依赖：仅 core IO，无模型。可与 P1 并行或穿插做。
- 预期产出：2–3 个模块 + 中文路径/EXIF 兼容测试。

## P3 · v0.6 识别与智能化（优先级：中）

| 功能 | 与图片处理的关系 | 说明 |
|---|---|---|
| OCR 文字识别 | 直接相关（识别） | RapidOCR / PaddleOCR 的 ONNX 版（与现有 onnxruntime 栈一致） |
| 分类打标 | 直接相关（识别） | CLIP/标签模型 ONNX 化，为图片写关键词、辅助检索 |
| 人脸检测裁剪 | 直接相关（识别+编辑） | 检测→自动裁剪证件照/头像，与 crop 模块联动 |

- 依赖：扩展 `downloads.py` 支持多权重（det+rec 模型对）；把权重状态条从 matting 专属抽成通用组件。
- 预期产出：1–2 个识别模块 + 通用「权重管理」组件。

## P4 · v0.7 平台化与发布（优先级：中远期）

- **模块串联 Pipeline**：抠图→超分→压缩一条龙。需扩展 `pipeline.py` 让 `ModuleResult.outputs` 可作为下一个模块的输入——框架级改动，放最后。
- **图片上传/分享**（可选）：导出到图床或本地 HTTP 分享，外围能力，优先级最低。
- **PyInstaller 打包 + GitHub Actions 持续发版**：原路线图 M6，与更新器（已就绪）闭环。

## 实施顺序与依赖小结

```
P1 超分/裁剪 ──(复用现有引擎)──> P2 转换/编辑（可并行）
P2 ──(ONNX 栈 + 权重管理扩展)──> P3 识别
P3 ──(pipeline 多模块串联改造)──> P4 串联 + 打包发布
交叉依赖：智能裁剪 ← matting mask；人脸裁剪 ← P3 检测；串联 ← P1/P2 模块都可用
```

## 统一验收标准

沿用项目惯例：

- smoke 测试通过（新增模块各自带测试脚本）；
- 中文路径兼容（统一走 `io_utils` 读写）；
- 无 GPU 时自动回落 CPU；
- `docs/开发日志.md` 按「现象 → 原因 → 改动 → 验证」记录；
- GitHub Release 发版，版本号按阶段递增。
